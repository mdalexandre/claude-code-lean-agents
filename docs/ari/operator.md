# ARI 3.0 operator

The operator is the layer that uses the ARI 2.0 tools without being invoked. One run is a **tick**: it observes, investigates the skills that are listed but never used, turns settled investigations into candidate changes, verifies changes you applied, regulates its own spending and writes a short brief. It proposes; it never applies a change, edits a skill, installs anything or approves on your behalf. Design and requirements: `docs/specs/ari-srd-v3.0.0.md`.

## Commands

```bash
python3 scripts/ari_operator.py tick --no-model     # code only: observe, probe, candidates, brief
python3 scripts/ari_operator.py tick                # also lets the model investigate open questions
python3 scripts/ari_operator.py brief               # the latest brief
python3 scripts/ari_operator.py status              # mode, counts, spend, integrity, every pending id
python3 scripts/ari_operator.py approve C-xxxxxxxx  # owner, at a terminal: type the shown code
python3 scripts/ari_operator.py applied C-xxxxxxxx  # owner: you applied it, start its canary
python3 scripts/ari_operator.py reject C-xxxxxxxx --reason "why"
python3 scripts/ari_operator.py resume              # owner: lift a suspension, restart the failure count
python3 scripts/ari_operator.py pin                 # owner: re-pin protected files after review
```

State lives in `~/.ari/operator` (override with `--state-dir`). Exit codes of `tick`: 0 OK, 3 SAFE, 75 BUSY (another tick holds the lock), 1 failed. `approve`, `applied`, `reject` and `resume` take the same lock and return 75 while a tick runs, so neither side can overwrite the other's write. `approve`, `applied`, `resume` and `pin` need you at a terminal: each shows a one time code on that terminal and you type it back (tested on a real pseudo terminal). `approve`, `applied` and `resume` also refuse while a protected file differs from its pin. `reject` needs neither, because it only removes a proposal. A rejected target gets no new candidate.

## What a tick does

1. **Integrity.** Every module in `scripts/ari/`, the operator's own command line `scripts/ari_operator.py`, the three programs a tick runs (`skill_mcp_audit.py`, `weekly_burn.py`, `ari_nightly.py`) and `tests/test_ari3_gates.py` are pinned by sha256 in `docs/specs/ari-protected-v3.json`. A mismatch puts the operator in the SAFE state: no investigation, no model call, the brief says why. Re-pinning needs you at a terminal. The check runs in code that is itself pinned, so it guards against accidental or agent edits, not against someone who can edit and re-pin as you. A `state.json` that cannot be read is kept aside as `state.json.unreadable-<tick>`, the tick continues with a fresh history, and the model layer stays suspended until you `resume`. An unreadable `candidates.json` or `investigations.json` is kept aside the same way (a file nested too deeply to parse counts as unreadable). A single candidate with a wrongly typed field (a canary start without a time zone, a waiting period over 3650 days, a probe spec that fails validation, a benefit that is not a finite number) moves to `candidates.quarantine.json`, and a single investigation that does not load (wrong field types, a missing root question) moves to `investigations.quarantine.json`; a quarantined candidate that is proposed again starts from CANDIDATE and needs your approval again. Unreadable lines of `model_runs.jsonl` are skipped. Each is an incident in the brief. Question depths are recomputed from the parent chain on load, so an edited depth cannot lift the depth bound. A lock or journal that is a folder or cannot be opened, and a plain file where a working folder (`evidence`, `model-cwd`, `observe`, `nightly`) belongs, are kept aside the same way. The SAFE brief is written even when the candidate store is unreadable. Any error that escapes all of this is written to `tick_crashes.jsonl` and the tick reports FAILED.
2. **Observe.** It runs `skill_mcp_audit.py`, `weekly_burn.py` (both over the same `--days` window) and `ari_nightly.py` (at most 14 days) as subprocesses and digests their output. Unchanged evidence wakes nothing. When the audit fails, its counts are unknown rather than zero: the tick records an incident and skips probing, candidate moves, canary checks and model rounds. A tool whose output has invalid bytes or JSON nested too deeply counts as a failed tool. Tool and model error text is screened before it reaches the brief or the ledger: secret shaped strings, the value after a keyword such as password, token, secret, api key or authorization, the value after bearer or basic, and the password part of a URL are replaced.
3. **Investigate.** For each listed but unused skill it asks (it opens up to 60 new investigations per tick, most expensive listing first; open ones are probed again when the evidence changes): unused, used indirectly, or a telemetry gap? When unused or indirect use is supported, a child question opens: redundant with another skill, demand that never routes to it, or dormant (a telemetry gap opens none). Every hypothesis names a probe from a closed catalog and its supports and refutes rules before the probe runs. The pair of rules must be able to support, able to refute, and never hold both at once over the values that probe can return, so a result is never decided before the probe runs. An ambiguous result stays open: only a probe result can settle a question. A model's "unresolved" verdict is refused when the hypothesis has a supporting result or when it would close the question or change its winner. Demand is judged by at least 3 distinctive words of the skill's description: words of 4 or more letters with no digits, excluding your ordinary vocabulary (a word found in more than max(3, 2% of your prompts) prompts). A skill with fewer than 3 distinctive words is left undecided.
4. **Model (optional).** Open questions go to `claude -p` with no tools, no MCP servers, hooks disabled, no session file and a spend cap. It may only return proposals (a new hypothesis, a child question, an unresolved verdict, an interpretation), each type with required fields, at most 8 per reply. The operator validates each one, applies it all or nothing, and runs every probe itself; a malformed proposal is refused and the call is still recorded with its cost. A missing or unreadable cost, and a call stopped by its timeout, count as the whole call budget. A question is offered once per evidence digest, whatever the outcome of the call, so a failed call is not paid for again on the same evidence. Before each call the offer is saved and a `call_started` row is written to the ledger: a call whose process is killed before its result is recorded counts at its whole budget and as a failed call, and is not asked again on the same evidence. A call that raises any error counts at its budget; token counts are capped at 10^12. Budget: USD 1 per tick and USD 5 per rolling 7 days; each call's cap is the smaller of what is left of the two, rounded down to the cent, and no call starts below USD 0.05. At most 3 calls per tick, each with at most 6 questions. Three failed calls in a row suspend the model layer until `resume`, which also restarts the count. Interpretations appear in the brief labelled as unverified model text.
5. **Candidates.** A settled investigation becomes a candidate: `restrict_exposure` (dormant), `consolidate` (redundant), `routing_correction` (unrouted demand), `telemetry_defect`. Recurring corrections you typed in three or more sessions become competence candidates after a holdout check. Each candidate carries the probe and rule that will judge it after you apply it.
6. **Lifecycle.** CANDIDATE, then REPLAYED (the conclusion reproduces on a later tick's evidence), QUALIFIED, APPROVAL_PENDING. Only you move it to APPROVED and, once applied, CANARY. After its window it becomes VERIFIED or ROLLED_BACK by its rule (probes that need parsed counts read the current audit), and per kind accuracy is kept. Each canary is judged on a window that starts at its own start time. It is not judged, and an incident says why, while transcript gaps are unread or when no transcript line was read for its window. A candidate whose content no longer matches the hash you approved is reported as an incident and is not judged, even when its stored hash was rewritten too; `applied` refuses it. An APPROVED or CANARY candidate without a matching approval record is quarantined. The approval prompt shows the verification rule (probe, arguments, supports and refutes rules, waiting period) as well as the proposal, with control characters shown as `?`. A kind whose outcomes roll back too often becomes a `policy_revision` candidate.
7. **Brief.** `brief.md` and `brief.json`: what changed, what ARI did, and at most three decisions. Benefits are shown with their unit. Units are never compared: they take turns in alphabetical order, each giving its best candidate, and decisions left out are counted with a pointer to `status`. Approved candidates waiting for you to apply them are listed. Incidents (SAFE, suspended model, failed tool, an unreadable state file, a candidate changed after approval) are always shown.

## Installing the schedule and the hook

Nothing is installed by the operator. When you decide to:

```bash
deploy/install_ari_operator.sh install     # nightly timer at 03:30 + SessionStart hook
deploy/install_ari_operator.sh status
deploy/install_ari_operator.sh uninstall   # removes both, keeps the state directory
```

`install` backs up `~/.claude/settings.json` first (one backup per run, never overwritten), adds one SessionStart hook that shows the brief once per day (to whichever session starts first that day, headless ones included), and then enables `ari-operator.timer` (03:30 with up to 10 minutes of random delay, catching up after a missed run). The service runs under `MemoryHigh=8G`, `MemoryMax=12G` and `MemorySwapMax=2G`, with a 2 hour start timeout.

## Limits

* A tick reads the last 14 days of transcripts. On the heavy test setup (about 33 GB of transcripts) code only ticks took 3.7 to 4.6 minutes and about 0.58 GB peak resident memory, measured with `/usr/bin/time -v` on 2026-11-02. A model round adds about 10 seconds per call; each `transcript_term_count` probe pass adds one more transcript scan.
* Prompts are what you typed: meta lines, sidechains and compaction summaries are excluded. Word matching is a proxy for demand, not proof of intent.
* The approval gate proves someone is at the terminal, not who. No local mechanism can tell you apart from a process running as your user; the tool-less model and the terminal check keep the model out of the approval path. The stored approval record is likewise not authenticated: a process running as you can edit `candidates.json` directly, and the content hash check only catches an edit that changes the candidate without matching its approval.
* A word you repeat in three or more corrections becomes part of a competence proposal. A single repeated word cannot be told apart from a password typed three times, so such a proposal can show it; screening applies to excerpts and error text, not to these words.
* The pin covers the listed files only. A new file added under `scripts/` (for example one named like a standard module, which the tools would import first) is not detected.
* The secret screen also drops harmless text that looks like a secret (long paths, identifiers, commit hashes, the words token or password).
* Benefits are estimates in their own units (listing tokens, matching prompts, sessions). They are not costs and not quota.
